How CloudQueryX Works

Most demos show a chatbot. CloudQueryX shows the part behind the chatbot: what gets remembered, what gets retrieved, and why it was selected.

01Storememory, docs, graph, events
02Retrievevector, text, freshness
03Rankrelevance and confidence
04Budgettrim to token limit
05Handoffformatted context

1. Store what matters

Save facts, preferences, decisions, documents, source snippets, entities, relationships, and events in one isolated context database.

2. Retrieve with evidence

Search memories, source chunks, graph relationships, events, full text, and pgvector embeddings. Every result explains why it matched.

3. Build an LLM-ready bundle

Rank, trim, and format the selected context into a token-budgeted bundle your app can send to any LLM provider.

Transparent memory

Users can see stored context instead of guessing what the assistant remembers. Bad or outdated facts can be reviewed and removed.

Provider neutral

CloudQueryX does not own the final answer. It prepares context, then your app decides which model should answer.

One scoped API key

External apps use a database-scoped key, so context stays isolated per user and per context database.

Why It Matters

Without a context runtime, teams wire memory together by hand. CloudQueryX makes context retrieval a product surface instead of hidden glue code.

Typical AI app

Application code stitches together a vector DB, SQL tables, custom memory rows, graph lookup, ranking, and prompt formatting before every LLM call.

  • Context logic scattered across app code
  • Hard to explain why a fact was selected
  • Token budget handled late in the prompt

With CloudQueryX

Your app asks CloudQueryX for a context bundle. CloudQueryX retrieves, ranks, explains, trims, and formats the context in one place.

  • One context runtime before the model call
  • Every item includes scores and reasons
  • Context is selected before handoff
